## 3. 合并范围

### 3.1 节点主数据

建议将P3-T2增量样表中的6个详细能力节点纳入V0.3.7候选节点主表：

1. `P3T2-N01 明确监控任务与账号权限边界`
2. `P3T2-N02 筛选当前告警并判断优先级`
3. `P3T2-N03 追溯历史告警与典型案例线索`
4. `P3T2-N04 创建或选择性能指标查询模板`
5. `P3T2-N05 查询指标并识别异常变化`
6. `P3T2-N06 结合日志形成监控结论与后续入口`

合并规则：

1. 不改写V0.3.6中已有的 `P3-T2` 任务骨架节点。
2. 不改写 `AU-04` 能力单元节点。
3. 保留6个新增节点的 `audit_status`、`review_required_type`、`risk_level`、`media_handling_status` 和 `professional_risk_type`。
4. 保留 `source_maturity=increment_trial` 和 `v03_maturity=increment_trial`。
5. 不把节点状态改成专业复核通过、媒体审查通过或可发布。

预计节点数量：

`151 + 6 = 157`

### 3.2 关系主数据

建议将P3-T2关系增量样表中的34条关系纳入V0.3.7候选关系主表。

关系类型覆盖：

1. 任务拆分详细节点：6条。
2. 直接递进：6条。
3. 支撑判断：5条。
4. 前置基础：1条。
5. 问题回流：3条。
6. 能力挂接：9条。
7. 资源证据：1条。
8. 后续分流关系包含在直接递进、问题回流和支撑判断中。

合并规则：

1. 不删除V0.3.6中已有 `P3-T2 -> P3T3-N01` 的任务级递进关系。
2. 新增 `P3T2-N06 -> P3T3-N01` 作为详细能力节点层分流关系。
3. `P3T2-N06 -> P3-T4/P4T1-N01/P5T3-N03/P6T2-N01` 进入候选关系表，但必须保留 `待专业复核` 状态。
4. `P3T2-MEDIA01 -> P3T2-N06` 作为资源证据关系进入候选关系表，保留 `待媒体审查` 状态。
5. 能力挂接关系进入候选关系表，但不改变AU-04、AU-05、AU-09、AU-10等能力单元定义。

预计关系数量：

`358 + 34 = 392`

## 4. V0.4风险治理处理

P3-T2的12条V0.4风险治理扩展记录不并入V0.3.7四张主数据表。

处理方式：

1. 继续作为旁挂式风险治理记录。
2. 在V0.3.7合并说明中列为P3-T2风险治理依据。
3. 在输入输出物治理清单中保留 `P3-T2风险治理扩展增量样表V0.4.csv`。
4. 后续若形成全局V0.4风险治理汇总表，再决定是否并入汇总。

不得做的事：

1. 不把 `overall_publish_gate_status=not_ready` 改为通过。
2. 不把 `professional_gate_status=pending` 改为通过。
3. 不把 `media_gate_status=pending` 改为通过。
4. 不把教学模拟数据、教材表格范围或AI推断写成真实行业标准。

## 5. 合并前结构检查

P3-T2增量已经完成以下检查：

1. 新增节点ID唯一，未与V0.3.6既有节点冲突。
2. 新增关系ID唯一，未与V0.3.6既有关系冲突。
3. 新增挂接ID唯一，未与V0.3.6既有挂接冲突。
4. 新增资产ID唯一，未与V0.3.6既有输入输出物治理记录冲突。
5. 关系端点均可回溯到V0.3.6既有节点、P3-T2新增节点或P3-T2新增资源挂接对象。
6. 挂接节点均可回溯到P3-T2新增详细能力节点。
7. V0.4风险治理记录均可回溯到新增节点或新增资源对象。
8. 输入输出物路径已复核，错误0、告警0。

因此，合并准备阶段不需要先做P3-T2 V0.3.6A修订。

## 6. 合并后必须保留的门禁

若后续生成V0.3.7候选主数据，必须保留以下门禁：

1. 专业复核门禁：告警优先级、指标阈值、TOP异常、典型案例、分流规则。
2. 媒体审查门禁：原教材网管截图、软件界面、站点或账号信息。
3. 数据安全门禁：账号、角色、登录记录、操作日志、安全日志、站点对象和告警记录。
4. 学生正文门禁：当前不是教材正文，不能说明学生已经能直接学懂。
5. 平台门禁：当前没有出版社平台接口、学习记录数据库或AI助手接入。
6. 教学验证门禁：当前没有真实一线教师和学生试用数据。
