## 3. 通过点

### 3.1 节点没有明显过碎

本次没有把以下对象升格为能力节点：

1. 天线参数条目；
2. 无线参数条目；
3. 承载网参数条目；
4. 核心网网元或QoS字段；
5. 仿真软件按钮；
6. 单张软件截图；
7. 单个随堂测试题；
8. CSI-RS案例中的单个指标。

这些对象均被下沉到资源卡、参数表、媒体审查对象、学习活动、评价表或风险治理记录中，符合“能力动作主线 + 专业分支资源”的拆分原则。

### 3.2 AU-06被实质补齐

V0.3.4中 `AU-06 优化实施与变更记录` 仍是骨架节点。本次6个详细节点覆盖：

1. 优化对象与实施边界；
2. 优化动作类型与责任边界；
3. 参数依据读取；
4. 实施步骤与回退检查；
5. 实施结果与变更凭据；
6. 复测验证入口和P4-T2交接。

这比在任务层写“5G网络优化方案实施”更可验证，也更能支撑后续资源、活动、评价和质量门禁。

### 3.3 与前后任务关系成立

P4-T1能承接P2-T3和P3-T3，并进入P4-T2：

1. P2-T3提供整改建议；
2. P3-T3提供参数异常清单和处理建议；
3. P4-T1把建议转成受控实施、变更记录和复测交接；
4. P4-T2根据复测交接清单识别验证场景和指标。

这个关系链条说明P4-T1不是孤立的软件操作任务，而是“问题识别与参数依据 -> 优化实施与记录 -> 结果验证”的关键节点。

### 3.4 V0.4扩展层验证价值成立

P4-T1暴露了此前任务未充分验证的风险：

1. 参数变更；
2. 工程授权；
3. 专业责任边界；
4. 仿真软件截图；
5. 变更记录；
6. 复测交接；
7. 案例适用边界。

V0.4字段能基本承接这些风险，但仍有字段细化空间。

## 4. 主要问题

### 4.1 工程授权和参数变更责任仍偏备注化

当前主要通过：

1. `professional_risk_type=authorization`
2. `review_required_type=professional;teaching_validation`
3. `gate_blocking_reason`
4. `gate_next_action`

表达工程授权和参数变更责任边界。

这能满足本轮试拆，但如果后续继续扩展优化实施类任务，建议考虑在V0.5或后续字段中新增更明确的 `engineering_authorization_type`、`parameter_change_risk_type` 或同类字段。

### 4.2 媒体治理压力较大

P4-T1原文图片数量多，且任务实施环节依赖非通用仿真软件截图。当前已标记为 `redraw_required` 或 `pending_media_review`，但仍需后续决定：

1. 哪些截图完全不用；
2. 哪些截图重绘为教学化参数表；
3. 哪些截图重绘为去厂商化流程图；
4. 是否需要出版社或软件方授权；
5. 重绘后是否仍能支撑学生学习。

这些未完成前，不能进入正式学生端或资源包。

### 4.3 原文知识准备仍需教材化重写

P4-T1原文中天线、无线、承载、核心网知识内容较多。当前增量表只完成图谱拆分，不代表学生正文已经可用。后续若制作教材页面，必须把这些内容重写为：

1. 先给实际问题；
2. 再说明为什么要看某类参数；
3. 再给低门槛解释和反例；
4. 再让学生完成可检查产出。

不能把原文知识准备直接搬进数字教材页面。

### 4.4 CSI-RS案例需专业复核

CSI-RS案例有教学价值，但涉及周期、时隙偏移、RI、CQI、MCS、CRC Fail、下行MAC速率等专业判断。当前只能作为待复核教学案例，不能作为已审核教材结论。

## 5. 对节点方案的修订建议

当前6节点方案暂不建议再拆细。

不建议新增的节点：

1. “调整天线参数”；
2. “调整无线参数”；
3. “调整承载网参数”；
4. “调整核心网参数”；
5. “进入数据中心界面”；
6. “查询无线侧配置数据”；
7. “查询核心侧配置数据”；
8. “修改CSI-RS周期”。

这些都是N02、N03、N04、N05下的资源、活动、案例或媒体对象，不应升格为能力节点。

可保留观察的问题：

1. N02“动作类型与责任边界”是否需要在专业复核后拆出“专业协同判断”；
2. N03“参数依据读取”是否需要根据学生难度拆成基础读法资源和案例应用资源；
3. N05“变更记录”是否需要与P4-T3报告输出形成更强关系；
4. 工程授权和参数变更风险是否需要后续字段升级。

## 6. 后续建议

建议下一步不是继续选择第六类任务，而是先做P4-T1增量的治理同步，并记录为当前第五类普通任务验证成果。

治理同步后，建议进入以下判断：

1. 如果目标是继续验证主数据扩展机制，可先评审P4-T1是否需要形成V0.3.4A小修订；
2. 如果P4-T1内部评审无阻断问题，再考虑是否进入下一版主数据合并准备；
3. 如果要继续验证其他任务类型，优先选择与P4-T1形成闭环的P4-T3或此前第二候选P3-T4，但不应马上批量拆全书。

无论选择哪条路线，仍不建议直接进入页面生产或工具链模块拆解。
