## 1. 评审口径

评审重点包括：

1. 节点颗粒度是否稳定；
2. 节点是否承载职业能力，而不是表格字段或话术条目；
3. 关系是否表达职业逻辑，而不只是原文顺序；
4. 资源、活动和评价是否服务学生动作；
5. 客户沟通、隐私信息、电话录音和处理承诺是否被治理；
6. 是否存在直接合并V0.3.3的风险。

## 3. 通过项

### 3.1 P1-T3作为第三类任务验证对象成立

P1-T3验证的是此前未覆盖的AU-01“场景、站点与投诉信息采集”。它与P2-T2、P3-T3的验证价值不同：

1. P2-T2验证问题处理类任务不能拆成操作清单；
2. P3-T3验证参数检查类任务不能误写成固定线性流程；
3. P1-T3验证投诉受理、客户沟通、信息记录、现场核实和投诉反馈类任务能否进入课程能力图谱。

因此，本轮选择P1-T3是合理的。

### 3.2 节点没有被拆成投诉类型清单

当前方案没有把普通投诉、紧急投诉、重大投诉、升级投诉、批量投诉、重复投诉等逐项升格为图谱节点，这是正确的。

这些内容更适合进入：

1. 投诉类型与紧急程度判断卡；
2. 投诉受理分类单；
3. 应答原则与升级边界卡；
4. 话术辨析和边界判断活动。

这符合“能力节点承载稳定职业任务，具体类型、话术、表格字段和案例下沉为资源、活动、评价或治理项”的原则。

### 3.3 P1到P2/P4的跨任务关系基本成立

P1-T3不是孤立的信息采集章节。当前关系表已经建立了必要连接：

1. P1T3-N02支撑P2-T1测试准备；
2. P1T3-N03进入P2-T1现场测试；
3. P1T3-N02支撑P2T3-N01分析任务来源；
4. P1T3-N04支撑P4T2-N01识别验证场景。

这些关系能把“客户投诉”连接到“测试、分析、验证”，方向正确。

### 3.4 已识别用户信息治理风险

当前节点表和挂接表已经把N01-N04纳入 `data_security` 审核类型，并为N02配置了 `P1T3-PRIV01 个人信息脱敏与授权检查`。这比把投诉信息表当普通表格处理更稳。

但这只是第一步，不足以直接进入主表合并。

## 4. 主要问题

### 4.1 N04颗粒度偏大，混合了两个不同能力动作

当前N04为：

> P1T3-N04 初步定位问题并沟通处理结果

该节点同时承载：

1. 根据现场核实结果形成初步问题类型；
2. 判断处理状态；
3. 选择客户反馈口径；
4. 填写后续跟踪要求；
5. 连接P4T2-N01结果验证场景。

问题在于，“初步定位”与“沟通处理结果”虽然连续，但能力属性不同：

1. 初步定位偏专业判断和后续任务路由，容易越界到AU-05网络问题定位；
2. 沟通结果偏职业表达、服务边界和客户跟踪，容易连接AU-08职业表达。

如果合并在一个节点中，后续资源、评价、数据安全和教师讲评都会变得混杂。学生可能不知道本节点到底训练“判断问题入口”，还是训练“对客户怎么说”。

评审判断：当前N04不建议直接合并主表。

### 4.2 N02隐私治理仍停留在备注和挂接层

N02已经识别姓名、地址、电话、录音等风险，但目前治理方式主要是：

1. `review_required_type` 中包含 `data_security`；
2. 挂接 `P1T3-PRIV01` 检查卡；
3. notes中说明必须脱敏。

这些处理足以支撑内部验证，但不足以支撑主数据合并后的长期治理。原因是后续如果批量拆全书，可能很难检索出所有涉及电话、地址、录音、客户等级和处理承诺的节点。

评审判断：短期可保留现有字段，但内部评审应提出字段规范后续升级方向，例如增加“个人信息类型”“是否脱敏”“是否涉及录音”“是否涉及处理承诺”等治理维度。

### 4.3 反馈话术资源仍需更强的编辑门禁

P1T3-C07和P1T3-C08已经把反馈话术作为资源卡处理，这是正确的。但话术类资源风险不止是专业复核，还包括：

1. 是否越权承诺；
2. 是否隐含不当责任认定；
3. 是否缺少客户同意；
4. 是否把不确定问题说成确定结论；
5. 是否把运营商内部流程写成对学生可直接套用的话术。

当前挂接表中已有 `pending_editorial_review`，但建议在修订版中把话术资源的审核重点写得更明确。

### 4.4 经典案例需要改写口径，不能直接进入5G教材资源

原文经典案例包括弱覆盖、测试正常、室内无覆盖等处理回复，教学价值存在，但案例语境偏4G，且具体地点、时间、人员信息有脱敏和适用边界问题。

当前已在挂接表中标注“案例偏4G语境”，这是必要的。但若后续进入资源包或学生正文，不能直接照搬，应转为：

1. 5G教学模拟投诉案例；
2. 脱敏案例；
3. 明确“本案例用于训练投诉信息整理和反馈边界，不作为真实处理规则”的案例。

### 4.5 与P4T2-N01的关系需要调整表达

当前关系EV032-INC-P1T3-013写为：

> P1T3-N04 -> P4T2-N01

如果N04拆分为两个节点，更合理的是：

1. 初步定位节点支撑P4T2-N01识别验证场景；
2. 沟通反馈节点支撑AU-08或后续报告表达，而不直接支撑P4T2-N01。

这能让跨任务关系更准确。

## 5. 修订建议

建议形成P1-T3 V0.3.2A修订增量。

### 5.1 节点修订

建议由4节点调整为5节点：

| 原节点 | 修订建议 |
| --- | --- |
| P1T3-N01 完成投诉应答、分类与升级判断 | 保留，标题可微调为“完成投诉应答与处理边界判断” |
| P1T3-N02 核实投诉关键信息并填写信息单 | 保留，强化“脱敏记录”和“可分析信息” |
| P1T3-N03 现场核实投诉场景与业务现象 | 保留，强调“不等于完整测试任务” |
| P1T3-N04 初步定位问题并沟通处理结果 | 拆分 |
| 新P1T3-N04 形成投诉初判与后续任务入口 | 承担专业初判、问题类型、后续测试/分析/验证入口 |
| 新P1T3-N05 沟通处理结果并形成跟踪闭环 | 承担反馈话术、客户沟通、处理状态、跟踪记录和服务表达 |

### 5.2 关系修订

建议内部主线调整为：

```text
P1T3-N01 -> P1T3-N02 -> P1T3-N03 -> P1T3-N04 -> P1T3-N05
```

跨任务关系建议：

1. P1T3-N02 -> P2-T1：投诉信息单支撑测试准备；
2. P1T3-N02 -> P2T3-N01：投诉信息单支撑数据分析任务来源；
3. P1T3-N03 -> P2-T1：现场核实触发测试执行；
4. P1T3-N04 -> P4T2-N01：投诉初判支撑验证场景识别；
5. P1T3-N05 -> AU-08：处理结果沟通和闭环表达支撑职业表达能力。

### 5.3 挂接修订

建议将当前N04挂接拆分：

1. `P1T3-C06 投诉原因初步定位案例卡` 归入新N04；
2. `P1T3-C08 经典案例回复辨析卡` 可拆分为初判案例复盘和反馈表达辨析，或暂时挂接新N04与新N05；
3. `P1T3-C07 处理结果反馈话术边界卡` 归入新N05；
4. `P1T3-RPT01 投诉处理反馈单` 归入新N05；
5. 新增或强化 `P1T3-W04 投诉初判与后续任务入口单`，用于评价新N04。

### 5.4 治理修订

建议在V0.3.2A修订说明中明确：

1. P1-T3不使用真实客户数据；
2. 所有投诉表、话术、录音、电话号码、地址和客户等级均以教学模拟或脱敏数据呈现；
3. 投诉升级和处理时限不作为通用运营规则，只作为教学化边界判断；
4. 反馈话术必须经过编辑复核，专业原因必须经过通信专业复核；
5. P1-T3只形成投诉初判和后续入口，不替代P2/P3/P4/P5/P6的专业定位、分析和验证。

## 6. 是否可以合并V0.3.3

当前不建议直接合并V0.3.3。

原因：

1. N04颗粒度和能力边界不稳；
2. 数据安全治理仍需要更明确的修订说明；
3. 反馈话术和处理承诺需要更强编辑门禁；
4. 经典案例需要5G教学化改写或明确适用边界；
5. 当前4节点版虽然结构校验通过，但教学结构仍有可预见风险。

推荐路径：

1. 形成 `reports/P1-T3增量补拆修订说明V0.3.2A.md`；
2. 生成P1-T3 V0.3.2A四张修订增量样表；
3. 对V0.3.2A做短内部复核；
4. 再决定是否进入V0.3.3合并准备。

## 7. 结论

P1-T3作为第三个普通任务增量验证对象成立，方向通过。

当前4节点增量技术上可回写，但不建议直接合并主表。主要问题不是“太稀碎”，而是N04偏粗，把专业初判和服务沟通混在一个节点中。更稳的方案是形成5节点V0.3.2A修订版：保留N01、N02、N03，拆分N04为“投诉初判与后续任务入口”和“处理结果沟通与跟踪闭环”。

下一步应制作P1-T3 V0.3.2A修订说明和四张修订增量样表，暂不进入V0.3.3合并、页面生产或工具链模块拆解。
