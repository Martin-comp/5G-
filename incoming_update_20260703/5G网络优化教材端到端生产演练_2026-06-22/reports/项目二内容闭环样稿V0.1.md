## 1. 项目二学习导入

网络测试不是“拿着手机出去跑一圈”，也不是“把软件报告导出来就算完成”。一次可用于后续分析的5G网络测试，至少要回答三个问题：

1. 这次测试要证明什么；
2. 采集到的数据能不能被别人继续分析；
3. 测试过程中出现异常时，是否留下了可复盘的处理记录。

本项目用一个校园场景训练这件事。

教学模拟情境如下：

某职业院校新建教学楼、图书馆和学生宿舍区已经完成5G覆盖优化。最近一周，学生在图书馆一层和宿舍北侧反映“视频会议偶尔卡顿、移动到宿舍楼转角时速率明显下降”。项目组要求做一次教学模拟DT/CQT测试，判断测试数据能否支持后续分析和复测验证。

本项目的学习路线不是简单的“任务1做完必然任务2，任务2做完必然任务3”。更准确的路线是：

```text
P2-T1 测试准备和执行
-> 如果测试顺利，形成测试LOG和测试资料包，直接进入P2-T3数据分析
-> 如果测试中出现设备、软件、数据保存、现场协调等问题，进入P2-T2问题处理
-> P2-T2处理后，再把可用数据和问题背景交给P2-T3
-> P2-T3输出测试数据分析报告，并连接后续P4-T2结果验证
```

你在本项目中要形成四类成果：

1. 一份说明“测什么、怎么测、按什么口径测”的测试任务与准备材料；
2. 一份能说明测试过程是否可靠的DT/CQT采集记录；
3. 一份只在出现异常时填写的问题处理闭环记录；
4. 一份把LOG、指标、异常和建议讲清楚的测试数据分析报告。

注意：本样稿中的路线、指标、LOG、软件界面和数据均为教学模拟。涉及真实路线、GPS点位、客户场地、测试LOG、软件截图、设备图片、人员联系方式和入场许可的内容，必须在正式使用前完成脱敏、重绘、授权和专业复核。

## 2. 本项目先看懂的一张图

项目二可以先用一张“主线加分支”图来理解：

```text
测试任务单
  |
  v
测试准备核对单
  |
  v
设备连接与软件配置检查
  |-------------------- 出现异常 --------------------|
  |                                                   v
  |                                           测试问题处理
  |                                                   |
  v                                                   |
DT路线/CQT场景规划                                    |
  |                                                   |
  v                                                   |
DT采集记录 + CQT业务测试记录 <-------------------------|
  |
  v
测试数据交付包
  |
  v
LOG导入、指标识读、异常判断、整改建议
  |
  v
测试数据分析报告
```

看这张图时要抓住一个关键点：`P2-T2` 是异常分支，不是必经台阶。测试顺利时，P2-T1可以直接进入P2-T3；测试不顺利时，P2-T2负责把问题处理清楚，让后续分析知道这份数据是否可用、哪里有风险。

### 2.1 学生先做什么，最后交什么

如果你第一次学习这个项目，可以按下面的顺序走：

| 学习步 | 你先做什么 | 做到什么算完成 |
| --- | --- | --- |
| 1 | 读测试任务，圈出测试对象、路线、CQT点位和业务类型。 | 能说清“这次测试要证明什么”。 |
| 2 | 检查资料、设备、软件、许可和数据安全边界。 | 能判断是否具备开始采集条件。 |
| 3 | 规划DT路线和CQT测试点。 | 能说明每个路线段和测试点为什么被选中。 |
| 4 | 执行教学模拟采集并记录异常。 | 能交出DT记录、CQT记录和异常事件记录。 |
| 5 | 如果出现设备、软件、GPS、入场或数据保存问题，进入P2-T2。 | 能说明异常是否影响数据可用性。 |
| 6 | 整理LOG和记录，进入P2-T3分析。 | 能输出一份有依据、有边界、有复测建议的测试数据分析报告。 |

本项目最终不是交“测试截图”，而是交一组可复核材料：测试任务单、准备核对单、路线与场景规划表、DT/CQT采集记录、必要的问题处理记录、测试数据交付包和测试数据分析报告。

## 3. P2-T1 任务1：DT/CQT测试准备和执行

### 3.1 学习情境

项目组给出一个测试任务：对“教学楼到图书馆再到宿舍北侧”的校园路线做一次DT测试，并在图书馆一层、食堂门口、宿舍北侧转角做CQT定点测试。

你不是马上打开软件采集。你要先弄清：

1. DT和CQT各自解决什么问题；
2. 本次测试要采集哪些数据；
3. 测试路线和测试点为什么这样选；
4. 设备、软件、SIM卡、GPS和数据保存是否准备好；
5. 采集结果怎样交给后续分析人员。

### 3.2 第一步：确认测试任务和指标口径

DT和CQT的区别可以先用一句话理解：

| 类型 | 通俗理解 | 本项目中的作用 |
| --- | --- | --- |
| DT路测 | 人或车沿路线移动，边走边采集网络状态。 | 看路线连续覆盖、移动过程中的速率波动、切换或掉线等问题。 |
| CQT定点测试 | 在固定地点反复测试业务质量。 | 看重点区域内语音、视频、下载等业务是否稳定。 |

本次教学模拟测试的任务单可以这样填写：

| 项目 | 示例内容 |
| --- | --- |
| 测试对象 | 教学楼、图书馆、宿舍北侧转角及连接道路。 |
| 测试目的 | 判断学生反馈区域是否存在覆盖弱、速率低或移动性异常线索。 |
| DT路线 | 教学楼东门 -> 图书馆南侧 -> 食堂门口 -> 宿舍北侧转角。 |
| CQT测试点 | 图书馆一层、食堂门口、宿舍北侧转角。 |
| 重点业务 | 视频会议、网页访问、下载业务。 |
| 重点指标 | 覆盖类指标、信号质量类指标、上下行速率、接入和保持情况、异常事件。 |
| 本课判断边界 | 本课只判断教学模拟数据是否支持初步分析，不代表真实网络验收结论。 |

这里要注意两个错误：

1. 不能只写“测试校园5G网络”，因为这样后续不知道要分析哪个区域、哪个业务、哪类指标；
2. 不能把本课练习阈值写成行业通用标准，因为不同项目、不同频段、不同场景、不同验收口径会不同。

本节点对应的学生产出是：`测试任务与指标口径确认单`。

### 3.3 第二步：准备资料、工具设备和入场许可

一次测试能不能顺利，不只看现场操作，也看测试前准备是否完整。

测试前至少要核对六类材料：

| 类别 | 需要准备什么 | 为什么重要 |
| --- | --- | --- |
| 工参和基础资料 | 站点编号、经纬度、PCI、频点、邻区关系、测试区域图层。 | 后续判断异常点是否与站点、邻区或区域有关。 |
| 测试工具 | 测试手机、SIM卡、笔记本、GPS、扫频仪或教学替代工具、充电和供电设备。 | 设备不稳定会直接造成LOG不可用。 |
| 软件环境 | 采集软件、后台分析软件、license、数据保存路径、报告模板。 | 软件无法授权或路径错误会导致无法采集或无法导出。 |
| 人员和路线 | 测试人员、司机或步测人员、测试时间段、行进路线。 | 保证测试过程可复盘。 |
| 入场和协调 | 图书馆、宿舍、食堂等场地许可或教学模拟许可。 | 未经许可不能采集真实场地数据。 |
| 数据安全 | 真实位置、人员、联系方式、LOG、截图是否需要脱敏。 | 防止把敏感数据直接进入教材或平台。 |

示例准备核对单：

| 核对项 | 状态 | 处理意见 |
| --- | --- | --- |
| 校园教学模拟路线图 | 已准备 | 只使用教学化地图，不显示真实详细坐标。 |
| 站点和邻区简化表 | 已准备 | 用教学编号代替真实站点名称。 |
| 测试手机和SIM卡 | 已准备 | 记录终端编号，不记录个人手机号。 |
| GPS或定位数据 | 待确认 | 若无法锁定位置，进入P2-T2异常处理。 |
| 采集软件license | 已准备 | 真实软件截图需重绘或替换。 |
| 数据保存路径 | 已准备 | 确认磁盘空间和命名规则。 |
| 图书馆入场许可 | 教学模拟 | 不使用真实联系人和真实审批信息。 |

本节点对应的学生产出是：`测试准备核对单`。

### 3.4 第三步：配置测试软硬件并判断是否能开始采集

设备连接检查不是形式。它决定后续数据是否可信。

开始采集前，应按顺序检查：

```text
测试终端
-> 数据线或无线连接
-> GPS状态
-> 采集软件识别状态
-> license状态
-> 业务测试账号或服务器信息
-> 数据保存路径
-> 试采集LOG
```

示例检查记录：

| 检查对象 | 正常表现 | 异常表现 | 是否进入P2-T2 |
| --- | --- | --- | --- |
| 测试手机 | 软件能识别终端，业务可正常发起。 | 终端未识别、频繁断连。 | 是 |
| GPS | 可显示位置变化，轨迹连续。 | 长时间无法定位或轨迹跳变。 | 是 |
| license | 采集软件正常启动。 | 授权过期或功能不可用。 | 是 |
| 保存路径 | 试采集文件可保存、可打开。 | 路径错误、磁盘不足、文件损坏。 | 是 |
| 业务测试 | 视频、网页、下载测试可发起。 | 服务器不可达或账号不可用。 | 视影响决定 |

如果这里出现问题，不要硬着头皮继续采集。继续采集可能得到一份“看起来有数据，实际不能用”的LOG。正确做法是先进入P2-T2，把异常记录清楚。

本节点对应的学生产出是：`设备连接与软件配置检查记录`。

### 3.5 第四步：规划DT路线和CQT测试场景

路线不是随便画。路线要覆盖“可能出问题”的位置，也要覆盖能对照的位置。

本项目可采用这样的规划：

| 测试对象 | 设计理由 | 采集重点 |
| --- | --- | --- |
| 教学楼东门 | 起点，通常人流集中。 | 起始接入、覆盖基础状态。 |
| 图书馆南侧 | 反馈视频会议卡顿。 | 速率、信号质量、业务体验。 |
| 食堂门口 | 人流波动大，可作为对照点。 | 高峰业务质量和容量线索。 |
| 宿舍北侧转角 | 反馈移动到转角时速率下降。 | 覆盖边界、切换或邻区异常线索。 |

DT路线记录表：

| 路段 | 方向 | 为什么经过这里 | 观察重点 |
| --- | --- | --- | --- |
| A段 | 教学楼到图书馆 | 连接两个主要学习区域。 | 覆盖是否连续。 |
| B段 | 图书馆到食堂 | 人流和业务量变化明显。 | 速率是否波动。 |
| C段 | 食堂到宿舍北侧 | 用户反馈集中。 | 是否出现弱覆盖、切换失败或异常事件。 |

CQT测试点记录表：

| 测试点 | 场景 | 业务 | 为什么选 |
| --- | --- | --- | --- |
| 图书馆一层 | 室内学习场景 | 视频会议、网页访问 | 对应卡顿反馈。 |
| 食堂门口 | 半开放高人流场景 | 下载、网页访问 | 观察容量和体验波动。 |
| 宿舍北侧转角 | 室外边界场景 | 视频、下载 | 对应移动中速率下降反馈。 |

本节点对应的学生产出是：`测试路线与场景规划表`。

### 3.6 第五步：执行DT采集并记录异常事件

执行DT时，学生要同时做两件事：采集数据，记录过程。

如果只采集数据，不记录过程，后续分析时就不知道异常是网络问题、设备问题还是测试过程问题。

示例DT采集记录：

| 时间段 | 位置 | 设备状态 | 业务状态 | 事件记录 |
| --- | --- | --- | --- | --- |
| 09:00-09:05 | 教学楼东门 | 正常 | 网页访问正常 | 开始采集。 |
| 09:05-09:10 | 图书馆南侧 | 正常 | 视频会议偶有卡顿 | 标记为重点观察段。 |
| 09:10-09:15 | 食堂门口 | 正常 | 下载速率波动 | 记录人流变化。 |
| 09:15-09:20 | 宿舍北侧转角 | GPS轨迹短时跳变 | 视频卡顿明显 | 进入P2-T2判断是否影响数据可用性。 |

这里的关键不是让学生背软件按钮，而是让学生形成过程意识：

1. 异常发生在什么时间；
2. 异常发生在哪个位置；
3. 是业务异常、设备异常、软件异常，还是现场环境异常；
4. 该异常是否影响LOG可用性；
5. 后续分析时是否需要标注边界。

本节点对应的学生产出是：`DT采集与异常事件记录`。

### 3.7 第六步：执行CQT定点测试并记录业务质量

CQT测试强调固定场景下的业务质量。学生要知道，同一个区域移动中表现不好，不一定等于定点业务也失败；反过来，定点业务正常，也不能证明移动路径完全没问题。

教学模拟CQT记录：

| 测试点 | 业务 | 第1次 | 第2次 | 第3次 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 图书馆一层 | 视频会议 | 可接入，偶有卡顿 | 可接入 | 可接入 | 需结合速率和SINR看原因。 |
| 食堂门口 | 下载 | 正常 | 正常 | 速率波动 | 可能与人流或资源占用有关。 |
| 宿舍北侧转角 | 视频会议 | 卡顿明显 | 可接入但速率低 | 卡顿 | 与DT异常段位置接近。 |

学生不能直接写“图书馆网络差”或“宿舍网络一定有问题”。更合格的写法是：

> 本次教学模拟CQT中，宿舍北侧转角视频会议业务表现不稳定，与DT异常段位置接近。该现象可以作为后续P2-T3分析线索，但还不能单独证明具体原因。

本节点对应的学生产出是：`CQT业务测试记录`。

### 3.8 第七步：保存LOG并移交测试资料包

测试结束不等于任务结束。只有数据能被后续分析人员打开、理解、复核，测试才算真正完成。

测试数据交付包至少包括：

| 材料 | 用途 | 风险边界 |
| --- | --- | --- |
| DT LOG文件 | 支撑路线指标和异常事件分析。 | 真实LOG需脱敏，不能直接放入教材。 |
| CQT记录表 | 支撑定点业务质量判断。 | 真实人员、电话、账号要删除或替换。 |
| 路线与测试点说明 | 说明数据从哪里来。 | 真实坐标和敏感场地需教学化处理。 |
| 异常事件记录 | 说明采集过程中的风险。 | 不能把设备异常误写成网络异常。 |
| 数据字段说明 | 帮助P2-T3分析人员读懂字段。 | 工具字段需解释，不能只贴软件表头。 |

建议命名规则：

```text
P2_schooltest_DT_20260626_teaching.log
P2_schooltest_CQT_record_20260626_teaching.xlsx
P2_schooltest_exception_record_20260626_teaching.md
P2_schooltest_handoff_list_20260626_teaching.md
```

本节点对应的学生产出是：`测试数据交付包`。

### 3.9 P2-T1完成标准

学生完成P2-T1后，至少要交付：

1. 测试任务与指标口径确认单；
2. 测试准备核对单；
3. 设备连接与软件配置检查记录；
4. 测试路线与场景规划表；
5. DT采集与异常事件记录；
6. CQT业务测试记录；
7. 测试数据交付包。

教师评价时不只看“有没有完成测试”，还要看学生能否说明数据来源、测试口径、异常事件和数据可用性。

## 4. P2-T2 任务2：5G网络测试问题处理

### 4.1 本任务什么时候进入

P2-T2不是每次都必须进入。只有当测试准备或测试执行出现异常，影响测试继续进行或影响数据可用性时，才进入本任务。

本项目给出三个常见异常：

| 异常 | 可能影响 | 是否进入P2-T2 |
| --- | --- | --- |
| GPS短时跳变 | 路线位置不连续，影响异常点定位。 | 是 |
| 采集软件license过期 | 可能无法采集或无法导出。 | 是 |
| 图书馆临时不允许进入 | CQT测试点无法完成。 | 是 |

如果学生把P2-T2写成“任务1之后固定做任务2”，说明还没有理解项目二的职业逻辑。

### 4.2 第一步：判断异常现象和影响范围

先不要急着处理，要先说清异常是什么。

示例异常判断单：

| 项目 | 示例 |
| --- | --- |
| 异常时间 | 09:15-09:17 |
| 异常位置 | 宿舍北侧转角附近 |
| 异常现象 | GPS轨迹短时跳变，视频会议业务同时出现卡顿。 |
| 影响范围 | 可能影响该路段异常点定位，不一定影响全部LOG。 |
| 初步类型 | 设备或定位数据异常；同时保留网络问题分析线索。 |
| 是否暂停测试 | 暂停并做试采集复核。 |

这里要训练学生区分两类问题：

1. 网络本身可能有问题；
2. 测试过程本身可能有问题。

如果不区分，后续就可能把“GPS漂移造成的位置错误”误判为“网络在某个点突然异常”。

本节点对应的学生产出是：`测试异常现象判断单`。

### 4.3 第二步：按排查路径处理设备、软件和数据问题

排查不能靠猜。可以按“设备 -> 软件 -> 数据 -> 现场”的顺序走。

示例排查路径：

```text
设备连接是否正常
-> GPS是否锁定
-> 软件是否识别终端
-> license是否有效
-> 数据保存路径是否正常
-> 试采集文件是否可打开
-> 异常是否影响当前测试结果
```

测试问题排查记录：

| 排查项 | 观察结果 | 处理动作 | 结论 |
| --- | --- | --- | --- |
| GPS连接 | 连接正常，但宿舍北侧转角附近短时漂移。 | 暂停30秒，重新锁定后继续。 | 该时段位置数据需标注。 |
| 采集软件 | 终端识别正常。 | 无需处理。 | 软件不是主因。 |
| LOG保存 | 文件正常保存。 | 复制备份。 | LOG可用，但异常时段需说明。 |
| 业务测试 | 视频会议卡顿与位置漂移同时出现。 | 后续P2-T3分析时同时检查网络指标和数据质量。 | 不直接下网络结论。 |

本节点对应的学生产出是：`测试问题排查记录单`。

### 4.4 第三步：完成现场协调和责任升级

有些问题不是学生一个人能处理的。

示例：

| 情境 | 应联系谁 | 合规表达 |
| --- | --- | --- |
| 图书馆临时不允许进入 | 教师或项目负责人 | “本测试点暂未取得入场许可，建议改为教学模拟点或重新申请。” |
| license不可用 | 软件管理员或教师 | “采集软件授权异常，当前不能继续正式采集。” |
| 真实客户场地涉及人员信息 | 项目负责人或数据安全人员 | “该信息不进入教材展示，需脱敏或替换。” |
| 测试中出现设备供电风险 | 教师或现场负责人 | “暂停测试，确认供电和设备安全后再继续。” |

学生要避免两类表达：

1. “我自己处理一下就行”，但实际涉及授权、安全或数据合规；
2. “让客户配合一下”，但没有明确责任路径和合规口径。

本节点对应的学生产出是：`现场协调升级记录`。

### 4.5 第四步：形成问题处理闭环记录和预案

问题处理结束后，要留下可复盘记录。

示例闭环记录：

| 项目 | 内容 |
| --- | --- |
| 问题现象 | 宿舍北侧转角DT测试中GPS轨迹短时跳变。 |
| 影响判断 | 影响该路段异常点定位，但LOG主体可用。 |
| 排查过程 | 检查GPS连接、采集软件、保存路径和试采集文件。 |
| 处理措施 | 暂停测试、重新锁定GPS、标注异常时间段、备份LOG。 |
| 处理结果 | 测试继续进行，后续分析需剔除或标注异常时段。 |
| 预防措施 | 测试前增加GPS稳定性试采集，关键路段设置人工事件标记。 |

这份记录的价值在于：P2-T3分析人员拿到数据后，知道哪里能用、哪里要小心、哪里不能直接下结论。

本节点对应的学生产出是：`测试问题闭环记录与预案`。

### 4.6 P2-T2完成标准

学生完成P2-T2后，至少要交付：

1. 测试异常现象判断单；
2. 测试问题排查记录单；
3. 现场协调升级记录；
4. 测试问题闭环记录与预案。

教师评价时要看学生是否做到了三点：

1. 能区分网络异常和测试过程异常；
2. 能说明异常是否影响数据可用性；
3. 能把处理结果交给P2-T3继续分析。

## 5. P2-T3 任务3：5G网络测试数据分析

### 5.1 学习情境

现在你拿到了P2-T1的测试数据交付包，以及P2-T2留下的异常处理记录。你要做的不是直接打开报告模板写结论，而是先判断这份数据能支持什么、不能支持什么。

本任务的目标是把测试数据变成可复核的分析结论：

```text
确认数据来源
-> 导入LOG并核对字段
-> 读懂关键指标
-> 判断覆盖类异常
-> 判断移动性或邻区异常
-> 形成原因链
-> 写出整改建议
-> 输出测试数据分析报告
```

### 5.2 第一步：明确分析任务和数据来源

分析任务单要先写清数据从哪里来。

| 项目 | 示例 |
| --- | --- |
| 分析对象 | 校园教学模拟DT/CQT测试数据。 |
| 数据来源 | DT LOG、CQT记录、异常事件记录、测试问题闭环记录。 |
| 重点区域 | 图书馆南侧、食堂门口、宿舍北侧转角。 |
| 重点问题 | 视频会议卡顿、移动中速率下降、宿舍北侧异常段。 |
| 数据边界 | 09:15-09:17位置数据存在GPS跳变，需要标注或剔除。 |

本节点对应的学生产出是：`数据分析任务单`。

### 5.3 第二步：导入LOG并核对报告字段

导入LOG不是为了“生成一个好看的报告”，而是为了确认报告字段能不能支撑判断。

字段核对表示例：

| 字段 | 用途 | 本课读法 |
| --- | --- | --- |
| 时间 | 对齐事件发生顺序。 | 找到视频卡顿和GPS异常发生时段。 |
| 位置或采样点 | 对齐异常区域。 | 注意GPS跳变时段不能直接当成真实位置。 |
| RSRP类字段 | 观察覆盖强弱。 | 本课只用于判断覆盖线索，不写成通用验收标准。 |
| SINR类字段 | 观察信号质量和干扰线索。 | 与速率、业务体验一起看。 |
| 上下行速率 | 观察业务体验。 | 不能单独证明覆盖原因。 |
| 切换事件 | 观察移动性问题。 | 需要结合邻区、信令或配置复核。 |
| 事件标记 | 对齐人工记录。 | 判断异常是否来自测试过程。 |

本节点对应的学生产出是：`导入导出流程记录和字段核对表`。

### 5.4 第三步：读懂关键指标和判断边界

下面是一份教学模拟数据。它用于训练读法，不代表真实网络验收阈值。

| 采样段 | 主要位置 | RSRP类读数 | SINR类读数 | 下行速率 | 业务表现 | 初步观察 |
| --- | --- | ---: | ---: | ---: | --- | --- |
| A | 教学楼东门 | -82 | 22 | 420 Mbps | 正常 | 覆盖和质量较好。 |
| B | 图书馆南侧 | -91 | 15 | 180 Mbps | 视频偶有卡顿 | 质量下降，需要继续看业务和容量线索。 |
| C | 食堂门口 | -88 | 18 | 230 Mbps | 下载速率波动 | 可能与人流或资源占用有关。 |
| D | 宿舍北侧转角 | -105 | 6 | 60 Mbps | 视频卡顿明显 | 覆盖和质量均弱，需重点分析。 |
| E | 宿舍北侧转角复测 | -96 | 11 | 120 Mbps | 可接入但不稳定 | 有改善但仍需观察。 |

学生读表时要避免“单指标下结论”。

更稳的读法是：

| 看到什么 | 能支持什么 | 不能直接说明什么 |
| --- | --- | --- |
| D段RSRP类读数较弱 | 可以作为覆盖不足线索。 | 不能单独证明根因一定是站点覆盖不足。 |
| D段SINR类读数较低 | 可以提示信号质量或干扰线索。 | 不能直接判断是外部干扰、重叠覆盖还是设备问题。 |
| D段速率低且业务卡顿 | 可以说明用户体验受影响。 | 不能说明一定由覆盖造成。 |
| GPS在D段短时跳变 | 说明位置数据需标注。 | 不能把跳变位置直接当成精确异常点。 |

本节点对应的学生产出是：`指标读法与边界表`。

### 5.5 第四步：判断覆盖类异常

覆盖类异常不是只看“一个数低”。要把位置、覆盖读数、业务表现和采集过程放在一起。

覆盖异常判断记录：

| 判断项 | 证据 | 判断 |
| --- | --- | --- |
| 异常位置是否集中 | 宿舍北侧转角多次出现业务卡顿。 | 集中，值得分析。 |
| 覆盖类读数是否偏弱 | D段RSRP类读数明显弱于A、B、C段。 | 存在覆盖不足线索。 |
| 业务是否受影响 | D段视频卡顿明显，下行速率较低。 | 体验受影响。 |
| 测试过程是否干扰判断 | D段存在GPS短时跳变。 | 位置需要标注，不能过度精确。 |
| 初步结论 | 宿舍北侧转角存在覆盖类异常线索。 | 需结合复测和专业复核，不写成最终工程结论。 |

学生可写成这样的判断句：

> 在本次教学模拟数据中，宿舍北侧转角同时出现覆盖类读数偏弱、信号质量下降和视频业务卡顿，说明该区域存在覆盖类异常线索。但该路段有GPS短时跳变记录，异常位置不能过度精确，需要在报告中标注数据边界。

本节点对应的学生产出是：`覆盖异常判断记录`。

### 5.6 第五步：判断移动性或邻区异常

移动性问题通常出现在“人或车移动过程中”。如果学生只看定点CQT，很容易漏掉。

本项目给出一个教学模拟事件：

| 时间 | 位置 | 现象 | 可能方向 |
| --- | --- | --- | --- |
| 09:14 | 食堂到宿舍路段 | 速率下降，业务开始卡顿。 | 覆盖边界或容量压力。 |
| 09:15 | 宿舍北侧转角 | 终端驻留小区变化，业务短时中断。 | 切换或邻区关系线索。 |
| 09:16 | 同路段 | GPS短时跳变。 | 测试过程异常，需要标注。 |
| 09:18 | 复测段 | 业务恢复但速率仍低。 | 可能仍有覆盖或移动性风险。 |

移动性异常不能只看“有没有切换”。更稳的证据链是：

```text
移动路径出现业务中断
-> 对齐时间和位置
-> 查看覆盖和质量指标变化
-> 查看小区变化或切换事件
-> 检查邻区或配置线索
-> 排除测试过程异常影响
-> 写出可能原因和复核需求
```

学生在本课中可以写：

> 宿舍北侧转角出现移动中业务短时中断，并伴随驻留小区变化和信号质量下降。该现象可能与覆盖边界、切换条件或邻区关系有关。但同期存在GPS跳变，且未进行信令级复核，因此只能写成移动性异常线索，不能写成已确认邻区漏配。

本节点对应的学生产出是：`移动性异常证据链`。

### 5.7 第六步：归纳问题类型和原因链

分析报告不能停留在“这里差、那里卡”。要把现象整理成原因链。

示例原因链：

| 现象 | 指标或记录 | 可能原因 | 处理方向 |
| --- | --- | --- | --- |
| 宿舍北侧视频卡顿 | 覆盖类读数弱、SINR类读数低、速率低。 | 覆盖边界或信号质量不足。 | 复测覆盖，检查站点覆盖方向或室内外覆盖条件。 |
| 移动中业务短时中断 | 驻留小区变化、业务短时中断。 | 切换或邻区关系风险。 | 检查移动性配置和邻区关系，必要时做信令复盘。 |
| D段位置不连续 | GPS短时跳变。 | 测试过程异常。 | 标注异常时段，必要时剔除该段精确位置判断。 |

这里要强调：原因链不是最终专家结论，而是学生把数据整理成可讨论、可复核的专业表达。

本节点对应的学生产出是：`异常问题清单和原因链`。

### 5.8 第七步：制定整改建议

整改建议不能写成“优化一下网络”。要写清楚建议对象、依据、风险和验证方式。

整改建议卡：

| 问题 | 建议动作 | 依据 | 风险边界 | 验证方式 |
| --- | --- | --- | --- | --- |
| 宿舍北侧覆盖类异常线索 | 对该区域进行复测并核查覆盖方案。 | 覆盖类读数偏弱、业务卡顿集中。 | 教学数据不能直接作为工程调整依据。 | 复测DT/CQT，比较覆盖和业务指标。 |
| 移动性异常线索 | 检查切换事件和邻区配置。 | 移动中业务短时中断，驻留小区变化。 | 未做信令级复核，不能写成已确认邻区漏配。 | 结合信令或配置表复核。 |
| GPS异常时段 | 标注或剔除该时段精确位置判断。 | P2-T2闭环记录显示GPS短时跳变。 | 不能把漂移点当成真实异常点。 | 复测关键路段。 |

本节点对应的学生产出是：`整改建议卡`。

### 5.9 第八步：输出测试数据分析报告并连接复测

一份可用的测试数据分析报告至少包含五段：

1. 测试任务和数据来源；
2. 测试过程和异常处理说明；
3. 关键指标读法；
4. 异常判断和原因链；
5. 整改建议和复测要求。

示例报告段落：

> 本次教学模拟测试覆盖教学楼、图书馆、食堂和宿舍北侧转角，数据来源包括DT LOG、CQT记录、异常事件记录和测试问题闭环记录。测试过程中，宿舍北侧转角附近出现GPS短时跳变，已在问题处理记录中标注，因此该时段位置判断不应过度精确。
>
> 从指标读法看，宿舍北侧转角同时出现覆盖类读数偏弱、信号质量下降、下行速率降低和视频业务卡顿，说明该区域存在覆盖类异常线索。移动过程中还出现业务短时中断和驻留小区变化，提示可能存在移动性或邻区关系风险。但由于当前样本未完成信令级复核，不能直接写成已确认邻区漏配。
>
> 建议对宿舍北侧转角进行复测，重点核查覆盖连续性、移动性事件和业务体验；同时检查GPS异常时段对数据定位的影响。后续若优化方案实施，应将本报告中的异常点、数据边界和复测要求交给P4-T2结果验证任务继续判断。

本节点对应的学生产出是：`测试数据分析报告和修订记录`。

### 5.10 P2-T3完成标准

学生完成P2-T3后，至少要交付：

1. 数据分析任务单；
2. 导入导出流程记录和字段核对表；
3. 指标读法与边界表；
4. 覆盖异常判断记录；
5. 移动性异常证据链；
6. 异常问题清单和原因链；
7. 整改建议卡；
8. 测试数据分析报告和修订记录。

教师评价时要重点看学生是否能把“数据、现象、原因、建议、边界”连起来，而不是只看是否会导出软件报告。

| 异常分支判断 | 判断是否进入P2-T2。 | 是否把测试过程异常和网络异常区分开。 |
| 指标标注 | 标出指标能支持的判断和不能支持的结论。 | 是否避免单指标下结论。 |
| 证据链排序 | 把现象、指标、事件和原因连成链。 | 是否能形成可复核分析。 |
| 报告修订 | 把过满结论改成有边界的专业表达。 | 是否包含依据、边界和后续建议。 |

### 6.3 评价产出

项目二的评价不应只用选择题。更适合使用过程性产出和报告性产出。

| 评价对象 | 合格表现 | 不合格表现 |
| --- | --- | --- |
| 测试任务确认单 | 能说明测试对象、业务、数据、口径和边界。 | 只写“测试5G网络”。 |
| 测试准备核对单 | 覆盖资料、设备、许可和数据安全。 | 只列设备，不考虑数据和授权。 |
| 异常处理记录 | 能说明异常影响范围和数据可用性。 | 把所有异常都写成网络问题。 |
| 指标读法表 | 能说明指标支持什么、不能支持什么。 | 单看一个数就下结论。 |
| 分析报告 | 能连接数据、现象、原因、建议和复测。 | 只有截图和结论，没有证据链。 |

## 7. 教师带教建议

项目二建议按“主线带学 + 分支插入 + 分析输出”的方式组织。

### 7.1 课堂组织

| 阶段 | 教师做什么 | 学生做什么 |
| --- | --- | --- |
| 导入 | 给出校园测试情境，追问“这次测试要证明什么”。 | 判断测试对象和业务场景。 |
| P2-T1主线 | 带学生完成任务单、准备核对、路线规划和采集记录。 | 形成测试资料包。 |
| P2-T2分支 | 在GPS跳变或license异常处暂停，追问“还能不能继续分析”。 | 填写异常判断和排查记录。 |
| P2-T3分析 | 带学生读模拟指标表，区分覆盖、移动性和测试过程异常。 | 形成原因链和分析报告。 |
| 讲评 | 对比“过满结论”和“有边界结论”。 | 修订报告表达。 |

### 7.2 关键提问

1. 如果没有明确测试任务，后面的LOG为什么可能没有价值；
2. CQT点位为什么不能只选一个“好测”的地方；
3. 设备异常和网络异常混在一起会造成什么误判；
4. 哪些指标能支持覆盖类判断，哪些不能单独证明根因；
5. 为什么“业务卡顿”不能直接等于“邻区漏配”；
6. 一份测试数据分析报告为什么必须写数据边界。

### 7.3 典型错误答案

| 学生说法 | 问题 | 修正方向 |
| --- | --- | --- |
| 跑完路线就算完成测试。 | 忽略任务口径、异常记录和数据交付。 | 改为“形成可分析的测试资料包”。 |
| GPS漂移也没关系，报告里看趋势就行。 | 忽略位置数据边界。 | 标注异常时段，必要时剔除精确位置判断。 |
| RSRP低，所以一定是基站覆盖问题。 | 单指标下结论。 | 加入SINR、业务、位置、复测和专业复核。 |
| 视频卡顿就是邻区漏配。 | 根因跳跃。 | 先写成移动性或邻区风险线索。 |
| 指标变好就可以验收。 | 混淆测试分析和结果验收。 | 把报告交给后续P4-T2验证。 |

## 8. 课程能力图谱绑定

项目二当前绑定到以下能力单元：

| 任务 | 主要能力单元 | 说明 |
| --- | --- | --- |
| P2-T1 | AU-02 | 测试准备、工具配置、路线场景规划、数据采集和资料交付。 |
| P2-T2 | AU-03/AU-05 | 异常判断、排障路径、现场协调和闭环记录。 |
| P2-T3 | AU-03/AU-05 | 数据来源确认、指标识读、异常判断、原因链和分析报告。 |

图谱表达必须保留“正常路径 + 异常分支”：

```text
P2T1-N07 测试数据交付包
-> P2T3-N01 数据分析任务单
-> P2T3-N02 LOG导入与报告导出

P2T1-N03 设备连接检查异常
-> P2T2-N02 问题排查记录
-> P2T3-N02 LOG导入边界说明

P2T1-N05 DT采集异常事件
-> P2T2-N01 异常现象判断
-> P2T2-N04 问题闭环记录
-> P2T3-N01 数据来源和问题背景
```

如果后续做前端原型，学生端不应把P2-T2排成固定第二站，而应显示为“测试异常时进入”的分支入口。

## 9. 出版和平台门禁

项目二涉及的数据和媒体风险比项目四更明显。正式进入资源包或平台前，至少要处理：

| 风险对象 | 当前处理 |
| --- | --- |
| 真实DT路线和GPS点位 | 使用教学模拟路线或脱敏地图。 |
| 真实测试LOG | 使用模拟数据或脱敏样本。 |
| 软件截图 | 重绘为教学化界面或替换为字段表。 |
| 测试设备图片 | 审查版权和安全边界后再用。 |
| 入场许可和客户接口人 | 不进入学生端展示，必要时用模拟角色。 |
| 指标阈值 | 标注为本课练习口径或项目口径，不写成通用行业标准。 |
| 整改建议 | 标注待专业复核，不作为真实网络操作处方。 |

## 10. P2-T3深样章锚点初判

本样稿初步判断：`P2-T3 5G网络测试数据分析` 更适合作为项目二的深样章候选。

理由：

1. 它承接P2-T1的测试数据交付包和P2-T2的问题处理记录；
2. 它能把学生从“会采集”推进到“会分析、会表达、会写边界”；
3. 它与项目四P4-T2结果验证形成前后衔接；
4. 它适合做表格、图示、证据链排序、结论修订等多样化学习活动；
5. 它比真实路测执行更适合先做静态教材样章和前端原型。

但这个判断仍需在项目二内容样稿内部评审后再确认。如果后续发现学生对测试准备和采集主线理解不足，P2-T1也可能需要做成更深的实践型样章。

## 11. 当前样稿边界

本样稿已经完成项目二内容闭环的初稿表达，但仍有以下边界：

1. 数据为教学模拟数据；
2. 术语、阈值和案例逻辑需通信专业复核；
3. 软件截图、设备图片和路线图不得直接使用原图；
4. 真实LOG和GPS点位不得直接进入教材；
5. 教师端这里只给出带教建议，还不是完整课堂组织工具；
6. 资源转化方向只是设计位，不代表动画、互动和小游戏已经制作；
7. 本样稿不是正式教材定稿，也不是出版社平台资源包。

下一步应对本样稿做内部评审，重点检查：

1. 学生是否能看懂项目二怎么学；
2. P2-T2异常分支是否足够清楚；
3. P2-T3深样章锚点是否成立；
4. 内容是否仍有大纲化、标题化或专业跳跃；
5. 是否具备进入项目二闭环原型制作的条件。
