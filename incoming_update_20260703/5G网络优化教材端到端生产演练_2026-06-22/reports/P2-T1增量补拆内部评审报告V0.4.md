## 3. 通过点

### 3.1 节点没有明显过碎

本次没有把以下对象升格为能力节点：

1. GPS吸顶天线；
2. 扫频仪；
3. 车载逆变器；
4. 加密狗；
5. FTP软件；
6. 软件安装截图；
7. 测试路线上的单个道路或点位；
8. 单个测评问题。

这些对象均被下沉到资源卡、核对表、媒体审查对象、评价表或风险治理记录中，符合前序图谱原则。

### 3.2 AU-02被实质补齐

V0.3.3中 `AU-02 测试准备与测试执行` 仍是骨架节点。本次7个详细节点覆盖：

1. 测试任务与口径；
2. 测试资料、工具和许可；
3. 软硬件连通性；
4. DT路线和CQT场景；
5. DT路测采集；
6. CQT定点业务测试；
7. LOG归档和资料移交。

这比此前只在任务层写“测试准备与执行流程排序”更可验证。

### 3.3 与前序任务关系成立

P2-T1能承接P1-T3，并进入P2-T2和P2-T3：

1. P1-T3提供投诉时间、地点、业务类型和现场现象；
2. P2-T1据此完成测试准备、路线规划和数据采集；
3. 测试异常进入P2-T2；
4. 测试LOG和交付包进入P2-T3；
5. 后续P4-T2和P5-T3可复用其路线、数据源和测试记录。

这个关系链条说明P2-T1不是孤立操作任务，而是P1信息采集到P2测试问题处理和数据分析之间的关键节点。

### 3.4 V0.4扩展层验证价值成立

P2-T1暴露了此前三任务未充分验证的风险：

1. 实训安全；
2. 车辆路测；
3. 位置数据；
4. 测试卡和终端标识；
5. 软件截图和设备连接图；
6. 入场许可和客户接口人；
7. 测试LOG交付包。

V0.4字段能基本承接这些风险，但仍有字段细化空间。

## 4. 主要问题

### 4.1 “实训安全”仍没有独立字段

当前只能通过：

1. `review_required_type=teaching_validation`
2. `teaching_validation_gate_status`
3. `gate_blocking_reason`
4. `gate_next_action`

表达车辆路测、现场测试、设备供电和入场测试安全边界。

这能满足本轮试拆，但如果后续继续扩展实训任务，建议考虑在V0.5或后续字段中新增更明确的 `training_safety_risk_type` 或同类字段。

### 4.2 位置数据治理仍偏粗

路线规划、CQT测试点、GPS打点和LOG交付包都涉及位置数据。当前可用 `personal_info_type=location` 和 `data_security_review_scope=location` 表达，但它无法区分：

1. 个人位置；
2. 站点位置；
3. 路测路线；
4. 客户场地；
5. 教学模拟地图。

短期可以通过备注和脱敏要求治理，长期需要更精细的位置数据字段。

### 4.3 软件截图风险较高

原文 `image79-image82` 涉及软件安装、设备连接、任务创建和保存LOG。当前已标记为 `redraw_required`，但仍需后续决定：

1. 是去厂商化重绘；
2. 还是用教学化流程图替代；
3. 是否完全不用原截图；
4. 是否需要出版社或软件方授权。

这些未完成前，不能进入正式教材页面或资源包。

## 5. 对节点方案的修订建议

当前7节点方案暂不建议再拆细。

不建议新增的节点：

1. “准备GPS设备”；
2. “准备扫频仪”；
3. “安装测试软件”；
4. “打开FTP上传测试”；
5. “保存LOG文件”；
6. “填写测试卡号”。

这些都是N02、N03、N05、N06、N07下的资源、活动或评价项，不应升格为能力节点。

可保留观察的问题：

1. N05和N06是否需要在专业复核后合并为“执行DT/CQT测试采集”；
2. 若实际教学中DT和CQT训练差异很大，也可以保留当前拆分；
3. 当前先保留拆分，因为两者在场景、数据、过程和安全边界上差异明显。

## 6. 后续建议

建议下一步不是继续拆第五类任务，而是先做P2-T1 V0.4增量的治理同步，并记录为当前第四类普通任务验证成果。

治理同步后，建议进入以下二选一判断：

1. 如果目标是继续验证主数据扩展机制，可选择P4-T1或P3-T4作为下一轮候选；
2. 如果目标是提高当前图谱稳定性，应先评审P2-T1与既有P2-T2、P2-T3之间的项目二内部链条，判断P2项目链是否已经形成较稳定的测试闭环。

无论选择哪条路线，仍不建议直接进入页面生产或工具链模块拆解。
